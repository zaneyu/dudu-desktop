## Final review findings and what changed

The final reviewer's report found two Critical, nine Important and ten Minor issues. The fix round addressed:

- **C1** the relay could return a 20-envelope page larger than the desktop's 64 KiB response cap, and the desktop retried that forever. The relay now bounds a poll page at 48 KiB (always at least one envelope; the 20-row cap still applies) and the desktop surfaces a `RelayProtocolError` status on the Connection page instead of tight-looping.
- **C2 / I1** a payload with JSON `null` text or reaction, or a Base64 decode failure before the try block, threw past the poll loop and faulted it permanently. Payload fields are now validated, decode happens inside the try, any non-cancellation decrypt failure is treated as undecryptable (stored without plaintext and acked so it drains), and the loop has a final catch that backs off and restarts cleanly.
- **I2** toast activation parsed the raw launch string on `&` while the Windows App SDK serialises arguments with `;`. The composition now reads the SDK's parsed `Arguments` map, the string parser accepts both separators, and one shared key=value helper replaced the two duplicated copies.
- **I3 / M6 / M9** `docs/privacy.md` now says a received envelope row is deleted when the note is saved to the jar (not on relay ack), that unsaved rows persist as ciphertext and appear in backups, that device deletion keeps the `devices` row, and links `protocol/README.md` correctly.
- **I4** the four `work/generated-package-locks/**/packages.lock.json` files tracked since `c37523f` were untracked; `work/` and `outputs/` are now in `.gitignore`; `verify.ps1` fails on any tracked `packages.lock.json` or tracked path under `work/`/`outputs/`, and the release docs no longer describe a "tracked exception".
- **I5 / I6 / M4** the sender page clears `draftMessageId` on 401 (no stale 409 after re-pairing), pins the desktop public key at pairing time and forces a visible re-pair on mismatch, and zeroes plaintext bytes on the 413 path.
- **I7** uninstall now deletes `{userstartup}\Dudu Desktop Companion.lnk` regardless of the keep-my-data choice; install and upgrade still never touch it.
- **I8** the e2e outage-reminder wait is `60 + 2 × dueReminderSeconds` seconds so a cold `dotnet run` build does not trip the gate.
- **I9** `ProductInfo.DefaultRelayBaseUrl` stays `null`; when `DUDU_RELAY_BASE_URL` is unset the Connection page shows "no relay yet notes stay local" instead of an exception message. `ResolveRelayOptions`/`TryParseAbsoluteHttpUri` are now unit-tested.
- **M1 / M3** router percent-decoding errors are a clean 400; `DisconnectSendersAsync` and `EnsureRegisteredAsync` zero PKCS#8 bytes.

Accepted as-is after review (recorded in the ledger with reasons): protocol version is not persisted per envelope (v1 only); pairing-code hash collision is a 500 (negligible); `novalidate` on sender forms; `NotificationsAvailable` latches false after one sink failure (spec-aligned, pet bubble fallback); `CaptureEnvironment` atomic read; T18 ack atomicity and cross-device duplicate-id race (fail closed); `SelfTestRunnerTests` duplicated between App.Tests (Windows) and Infrastructure.Tests (runs here); harness `Task.Delay` without token; `DuduUiFixture` polling duplication.

Also outstanding: `relay/wrangler.jsonc` still carries the placeholder D1 `database_id` `00000000-0000-0000-0000-000000000000`; `docs/release.md` §3 describes creating the real database and pasting the id.

## Incident during Task 24 (needs your attention)

While verifying command names, the Task 24 implementer ran `npx wrangler deploy -- --help` and `npx wrangler rollback -- --help` inside `relay/`. Wrangler ignores the trailing `--help` in that form and executed both commands for real against the Cloudflare account that was already authenticated on this Mac. The deploy uploaded the ten static files under `relay/public/` to an asset upload session and then failed with D1 error 10181 because of the placeholder `database_id`; `wrangler deployments status` afterwards reports that the Worker `dudu-relay` has no deployments. No secrets were read or written and no D1 database was created. Nothing was left running, so there is nothing to roll back from here, but you may want to check the Cloudflare dashboard for the `dudu-relay` Worker and any dangling asset session. `docs/release.md` §3 now warns about this footgun.
